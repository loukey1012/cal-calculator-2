## A · Quick fixes

### 32 · Swipes at the bottom close the screen (bug, highest priority)

- User: swiping along the bottom (iOS home indicator, switching apps) or up into the app switcher
  closes the screen they're on; they lost a new ingredient's values five times.
- Cause (found in `src/app/PageStack.tsx`, "the back swipe"): the back swipe starts from **any**
  touch point and only decides by direction (`dragDirection`). The home-indicator swipe to the
  next app is a sideways touch that starts inside the page, so it's taken as Back and the
  page pops (`onBack`), unmounting the form.
- Fix:
  - ignore touches that start in the bottom strip: `touch.clientY > window.innerHeight -
BOTTOM_EDGE_PX` (≈ 44 px, the home-indicator area incl. `env(safe-area-inset-bottom)`; the
    user's iPhone: bottom inset 34 px, see memory reference-user-iphone);
  - handle `touchcancel` (iOS sends it when the system takes the gesture over): cancel the drag,
    slide the page back, never complete Back;
  - check the tab carousel (`TabShell.tsx`, Embla) and `Sheet.tsx` drag-to-dismiss for the same
    two problems (a bottom-start and a cancelled gesture must not switch tabs or dismiss).
- Safety net: the new/edited ingredient form keeps its unsaved values on the phone like the Cook
  draft (`cook/draftStorage.ts` pattern: versioned localStorage key per user, Zod-validated,
  cleared on save/cancel), restored when the form opens again for the same ingredient (or "new").
  Covers iOS killing the app in the background too.
- Tests: PageStack unit tests with synthetic touches (bottom start ignored, touchcancel cancels);
  form draft restore test; a journey that types values, simulates a cancelled swipe, and keeps
  them.

### 33 · Keyboard ✓ moves to the next value field

- User: on the iPhone a floating bar above the number pad has a ✓ that closes the keyboard (works
  like OK). After entering a value and tapping ✓, the cursor should move to the next value field
  with the keyboard staying open; after the last one, the keyboard closes.
- Facts: value fields use `inputMode="decimal"` (`ingredients/BasisSection.tsx`,
  `IngredientForm.tsx`, `SplitPortionRow.tsx`); the decimal pad has no return key, so there is
  no keydown to catch. The ✓ only blurs the field.
- Approach (needs testing on the user's iPhone):
  1. On `blur` of a value field that wasn't caused by touching something else (no `pointerdown`
     in the last ~300 ms and `relatedTarget` null) → focus the next value field in order (a
     `useFieldSequence` hook with refs). Whether iOS opens the keyboard for a programmatic
     `focus()` after the system ✓ is uncertain.
  2. If not (likely on iOS), fallback: our own small **Next** button pinned to the top of the
     keyboard, right above iOS's own bar (user, 2026-10-20: fine as long as it sits on the
     keyboard, **not on the page**), via `visualViewport` (resize/scroll events give the
     keyboard's top); only while a value field is focused, it goes with the keyboard. "Next"
     focuses the next field from a real tap (iOS keeps the keyboard); on the last field it says
     "Done" and blurs. Sketch: board "33".
- **As built (2026-10-20):** went straight to the Next button (`components/ios/KeyboardNextButton`,
  used by `IngredientForm` for its `inputmode="decimal"` fields), since iOS only opens the keyboard
  for a focus from a real tap in the page; the ✓ keeps closing it. Check on the device that the
  button sits right on the keyboard (visualViewport) and that Next keeps the keyboard open.
- **32 as built:** `stackMotion.startsAtBottomEdge` (44 px) for the back swipe and the tab
  swipe; `touchcancel` slides the page back (`PageStack` `onCancel`); ingredient drafts in
  `ingredients/ingredientDraft.ts` (key household + ingredient id or `new:<barcode>`), restored
  with "Restored what you typed before · Discard" by the `IngredientForm` wrapper. Test setup now
  clears localStorage after every test.

### 38 · Categories redone

- User chose **two levels**: broad categories are the familiar ones (Meat & Fish, Dairy, …), the
  specific ones go inside (Leberkäse, Chicken, Gouda …). The current top level ("Fresh", "Bread &
  Carbs", …) disappears. **An ingredient can only get a specific category.**
- Today (prod, 2026-10-20): 6 groups (`category_groups`) → 13 categories (`categories`), 198
  ingredients, 3 without a category, one category named "ahead" (2 ingredients; likely a typo).
- Schema: stays `category_groups` (broad) → `categories` (specific) → `ingredients.category_id`.
  New rules (migration): `categories.group_id` not null (every specific category sits in a broad
  one) and **`ingredients.category_id` not null** (user, 2026-10-20: every ingredient must have a
  category; the 3 without one get one in the draft tree). The ingredient form's picker is two
  steps: broad first, then a specific one of that broad (replaces sketch "38 · Picking a category");
  saving without a category is refused with a clear message.
- User, 2026-10-21: "Snacks & Drinks" becomes two broad categories (Snacks, Drinks); a broad
  category where oat milk (Hafermilch) fits; picking a category is a **two-step choice**: first
  the broad one, then a specific one inside it (not one list of every specific category).
- Tree (2026-10-21, reviewed by the user in three rounds): `scripts/recategorize/tree.json`, 12
  broad → 49 specific, all 199 prod ingredients placed by "name (brand)". Old categories not in
  the tree (incl. "Hafermilch", made by the user on 2026-10-21) are removed once empty.

### 39 · Review merges duplicates

- User chose: merging is only offered from review findings (kind `duplicate`).
- The finding opens a compare view: both ingredients side by side, differences highlighted (name,
  brand, per-100 g and per-unit values, unit name and weight, measure, barcode, category, estimate
  flag, how often used: `ingredient_use_counts`). Pick which one to keep; optionally take single
  values from the other one (per row).
- Merge = RPC `merge_ingredients(p_keep, p_drop, p_patch jsonb)` (security definer, household
  check like `save_dish`): applies the patch to the kept one, repoints `meal_items`, `dish_lines`,
  `recipe_lines` (`ingredient_id`), moves the barcode if the kept one has none (unique per
  household!), deletes the dropped one, marks the finding applied. Logged food keeps its values
  (snapshots). Live hints follow from the triggers.
- Review findings reference ingredients: a finding about the dropped one must not break (FK on
  delete?). Check `review_findings.ingredient_id` behaviour.
- Tests: DB tests for the RPC (repointing, barcode move, other household refused), UI test for
  the compare view, a journey.
