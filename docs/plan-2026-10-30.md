**Decided design**

- **Chips, in this order:**

## Batch N — 71: notifications for everything the partner changes on my day

Push **N** (migration and function first, then the app commit with the renamed switch, README and
patch note).

**How it works today**

- Triggers on `meal_items` (insert, update, delete) and `meals` (`update of cheat_meal` or delete)
  call `private.note_partner_change`.
- That function writes `partner_changes (user_id, actor_id, date, meal_type, changed_at)`, one row per
  meal.
- `push-tick` (`partnerMessages`) waits until nothing new came for 3 minutes (`isQuiet`), deletes the
  rows, and sends one notification per actor (`partnerChangeMessage`, "baby changed your meals ·
  Today: Lunch, Dinner"). It then claims `push_sent` (kind `partner`, key `actor:latest`). Rows older
  than 24 h are cleared (`housekeeping`).
- Not covered today: cheat days, gym, day notes and meal notes. Resending the same cheat meal or
  cheat day from the offline queue counts again today (trigger fires on any update).

**Decided design**

- **What counts:** everything the partner changes on any of my days, today and past days:
  - meals (as now);
  - flags: cheat day / alcohol day, cheat meal, gym;
  - notes: the day note and meal notes.

  **Sex never** (no trigger on `sex_days`; a database test proves it). My own changes, and changes
  without a signed-in person (scripts, service role), are never noted (unchanged rule).

- **A flag is never named.** The message says only "a flag" / "flags", never gym, sex, cheat or
  alcohol (tested).
- **Flag changes that cancel out are dropped:**
  - each flag row keeps the value from before the first change not told yet (`before`);
  - at send time the tick compares it with the current value, and drops the row if they are equal
    (e.g. the partner set Gym and tapped Undo);
  - if nothing is left, nothing is sent and the rows are cleared.

  Notes and meals are told as now.

- **Grouping:**
  - unchanged rule: everything since the last notification goes out together, once no new change
    came for 3 minutes (`PARTNER_QUIET_MINUTES`); with the 5-minute tick that is about 3–8 minutes;
  - one notification per actor, all days together;
  - no quiet hours.
- **Wording** (`partnerChangeMessage` v2):
  - **Parts:** "your meals" (any meal change), "a flag" / "flags" (distinct flag rows), "a note" /
    "notes". Joined in this order as an English list ("your meals, a flag and a note").
  - **One day:** title = `<name> changed <parts> <day>`, where `<day>` is "today", "yesterday", "on
    Tuesday" (the last 6 days) or "on 20 Oct". The body lists the details: meal names in meal order,
    then "a flag" / "2 flags", "a note" / "2 notes". There is no body when it would only repeat the
    title (no meals).
  - **Several days:** title = `<name> changed <parts>`. The body has one line per day, newest first,
    joined with " · ": "Today: Lunch · Tue 27 Oct: a flag, a note".
  - **Examples:**
    - "baby changed your meals today" / "Lunch, Dinner"
    - "baby changed a flag on Tuesday" (no body)
    - "baby changed your meals and a note on Tuesday" / "Dinner, a note"
    - "baby changed your meals, a flag and a note" / "Today: Lunch · Tue 27 Oct: a flag, a note"
  - **Link and tag:** the newest day (`/today` or `/history/<date>`), tag `partner` (as now).
- **Settings › Notifications:** one switch, renamed "Changes to your meals" → **"Changes to your
  days"**. It keeps the stored field `partnerChanges` (no new field, so no new default or re-parse).
  Footer: "Meals, flags and notes your partner changes on any of your days, in one notification once
  they stop for a few minutes. Which flag it was is never said." (See question 2 for three switches
  instead.)

| Risk                                                        | Mitigation                                                                                                             |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Today no longer fits the screen                             | measure first, trims without a style change, question 1 as fallback; `today-layout.spec.ts`                            |
| A sideways drag on the chip row switches tabs               | `data-swipe-lock`, as on the category chips; journey drag check                                                        |
| A chip tap before its data loaded overwrites a mark         | each chip disabled until its own query has data (rule from `DayOptionsSheet`); test                                    |
| Undo lost or wrong offline                                  | Undo is a new queued, idempotent change with the exact previous value; same `scope` keeps the order; hook tests        |
| Chip label unreadable on a filled colour                    | `--on-mark`, 4.5:1 checked in `markContrast.test.ts` for all four themes                                               |
| Quick look closing under the finger, or staying open        | pinned after release; closes on outside tap, Escape or month change; gesture tests                                     |
| Calendar cell lags behind a cheat/alcohol toggle            | optimistic month-totals mirror with rollback; test and journey                                                         |
| Gym, sex, cheat or alcohol named in a push                  | one generic "flag" kind in the database; wording test with a forbidden-words regex                                     |
| Sex mark reaching a notification                            | no trigger on `sex_days`; database test                                                                                |
| Queue replays sending again                                 | `when … is distinct from` on updates; ignore-duplicates upsert for gym; database tests                                 |
| Flag set and undone still notifies                          | `before` kept from the first change; `stillChanged` at send time; unit test and dev smoke                              |
| A trigger error failing a save                              | every trigger function catches and only raises a warning (existing pattern)                                            |
| Old function running against the new table                  | function deployed to prod right after the migration; the failure is per person and caught; rows wait for the next tick |
| Pending rows lost by the migration                          | existing rows migrated (`subject = meal_type`), not deleted                                                            |
| Known noise: an ingredient edit or shared dish re-logs both | unchanged on purpose; noted in CLAUDE.md "Where to look"                                                               |
