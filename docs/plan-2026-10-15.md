# Build plan, 2026-10-15

The working plan for README items 1–15 ("Fixes and improvements (planned)"). The README has the
user-facing wording; this file has the decisions, the technical approach and where to start, so a
new session can pick up any item. **Update the status table after every item** (commit ref), and
tick the item in the README in the same commit.

## How to work on this project

- **Plan approved 2026-10-15? → see Status.** Build 2–3 items, push, then stop with a short
  summary so the user can test on the iPhone (user rule, 2026-10-15). Also stop for a real
  question, or where an item says "user picks".
- **TDD**: write the failing test first (Vitest + Testing Library next to the file, `*.test.ts(x)`;
  DB behavior in `supabase/tests/*.test.ts` against the DEV project; user journeys in
  `e2e/journeys/*.spec.ts`). Coverage must stay ≥ 80 % (`pnpm coverage` enforces it).
- **Before every push**: `pnpm lint && pnpm typecheck && pnpm format:check && pnpm test`, the
  affected e2e journeys (see README › Development; in WSL add `E2E_BROWSER=chromium`), and
  `pnpm test:db` when migrations changed.
- **Push to `main`** (Vercel deploys it). Don't wait for CI: report at once, and check the
  previous run (`gh run list`) at the start of the next item. If it's red, fix that first.
- **Patch notes (from item 21 on)**: every commit adds an entry to the patch notes in the same
  commit (date and hour, local time, and what changed in plain, neutral words; internal-only
  changes get one short line). See item 21.
- **Commits**: conventional (`feat:`, `fix:`, …), one per item or step. **No docs-only commits** (user, 2026-10-19): changes to docs, README, CLAUDE.md or this plan wait
  for the next functional commit. **The README is updated in
  the same commit** as any feature, setup, CI or architecture change.
- **Migrations**: `supabase/migrations/<yyyymmddhhmmss>_<name>.sql`. Push to **DEV first**
  (CLI is normally linked to dev), run `pnpm test:db`, then link PROD, push, and relink DEV.
  Regenerate `src/lib/database.types.ts` with `pnpm db:types`. Prod pushes may be blocked by
  the permission classifier. If so, commit locally, don't push app code that needs the
  migration, and ask the user.
- **UI copy**: short, neutral, professional ("Save", "Log meal"). No playful or personal text.
  Partner nicknames only where a person is identified (`useLookOf()`).
- **Settings are account-bound**: preferences live on the profile (`profiles.appearance` jsonb
  or a new column), never device-only. localStorage only as a launch cache.
- **iPhone**: a 390×844 home-screen PWA on iOS 27. No browser emulates its safe areas or
  viewport quirk. Never remove `--viewport-shortfall` or `stable-paint-layer` as dead code.
  The user can't send screenshots. Ask them for on-device confirmation in words.
- **Scripted edits**: read a file into a variable before `open(p, 'w')`, and check for empty
  files afterwards.
- Never: water tracking, invite-code rotation, xtool (checked 2026-10-15: device-only native
  builds, no iOS Simulator on Linux, doesn't help testing a PWA).

### 3 · Ingredient edits reach meals of the last 14 days

- Decision: **automatic**, window = **today and the 13 days before** (rolling, by the meal's
  local date), **both people's meals**. Older meals keep their snapshot. After saving, a toast:
  "Updated in N meals" (nothing when N = 0).
- This reverses part of the snapshot design (README › Features says "editing an ingredient
  later never changes past meals"). Update that README sentence when it ships.
- **As built (2026-10-15):** done in the app, not as an RPC, to reuse the tested `buildMealItem` /
  `resolveAmount` instead of porting them to SQL: `ingredients/applyToRecentMeals.ts` (plain items
  updated directly, dishes saved as a new revision through `save_dish`), triggered by
  `IngredientSheet`'s `onUpdated` on the Ingredients tab. Journey: `e2e/journeys/recent-meals.spec.ts`.
- Original idea: an RPC `apply_ingredient_to_recent_meals(p_ingredient_id, p_since date)` (security
  invoker or a checked definer, household-scoped):
  - update the `meal_items` snapshot of plain items with that ingredient in meals ≥ `p_since`
  - update the `dish_lines` snapshot of dishes that have a portion in the window, bump the dish
    revision, and re-log them with `private.log_dish_portions(dish_id)`
  - return the number of distinct meals touched.
- The client passes `p_since` = local today − 13 (`lib/dates`). Call it right after a
  successful ingredient update, then invalidate the day/history queries. Live hints already
  fire from the table triggers.
- Tests: `supabase/tests/` (plain item and dish inside/outside the window, the other member's
  meal, another household untouched), plus the unit test for the toast.

### 9 · Read nutrition labels (on-device)

- Decision: **on-device OCR** (no AI service). It must work offline after first use and must
  only load when first used.
- Approach: `tesseract.js`, lazy `import()`, German + English trained data. Serve or cache the
  language files so they work offline (Workbox runtime cache).
- Pure, well-tested parser `labelParser.ts`:
  - finds the per-100 g/ml column
  - maps row names (DE: Brennwert/Energie, Fett, davon gesättigte Fettsäuren, Kohlenhydrate,
    davon Zucker, Ballaststoffe, Eiweiß, Salz; EN equivalents)
  - handles kJ/kcal and decimal commas.
- Entry point: a **Read label** button next to the barcode scan in the ingredient form (camera
  or photo).
- It fills the form like the Open Food Facts prefill (`barcode/useProductPrefill.ts`,
  `PrefillNote`), the user checks, and **it never saves by itself**. `valueChecks` warnings
  still apply.

- **As built (2026-10-19):** tesseract.js 7 (LSTM only, `best_int` deu + eng from
  `@tesseract.js-data`). `vite.config` `ocrAssets()` serves the worker, the three LSTM engines
  (tesseract.js picks relaxed SIMD / SIMD / plain) and the language files at `/ocr/<version>/`
  (dev middleware + emitted into the build); Workbox leaves `ocr/**` out of the precache and keeps
  it in a CacheFirst runtime cache "ocr"; vercel.json caches `/ocr/` for good. Entry point: **Read
  nutrition label** as the first row of **Fill in values** (`label/ReadLabelRow`), not next to the
  barcode: that section already has Undo. `label/recognize.ts` (downscale to 2000 px, worker per
  read, absolute URLs, `workerBlobURL: false`, `cacheMethod: 'none'`), `label/labelParser.ts`
  (first number of each row = per 100 g; a trailing "9" is a misread "g" when the unit is missing
  or the value > 100), `label/labelForm.withLabelValues` (replaces only per 100 g + measure).
  Journey `label.spec.ts` runs the real engine on a rendered table.

- **Auto-crop (2026-10-19, after the user's test: small tables on big packages weren't read):**
  `label/tableRegion.ts` finds the table from pass 1's word positions, anchored on header and
  energy words (Nährwerte, Energie, Brennwert, kcal, kJ; ingredient lists also say Zucker/Salz),
  down 26 text heights, widened to the value columns; `enlargement` scales the cut-out to ~24 px
  letters (0.4–2.5×: 3× made the engine read only the first line); `enhanceContrast` grey +
  stretched. `recognize.ts`: pass 1 at 3200 px (again at 1600 when nothing is found: letters of
  ~100 px aren't read), pass 2 on the cut-out from the full-size photo, **PSM.AUTO** set
  explicitly (tesseract.js defaults to SINGLE_BLOCK, which garbles bordered tables). Parser:
  column-by-column tables, ingredient lines and the "pro 100 g" header skipped, l/I/| → 1 and
  O → 0 next to digits; `bestReading` fills the best reading's gaps from the other. Measured on
  rendered tables in the dev browser (a debug script importing `/src/features/label/*.ts` via
  Vite) — reuse that to diagnose real photos.

- Testing:

  - DB tests for the triggers and queue

### 14 · Recipes (+ copy a meal)

- Decision: recipes and meal templates are **one feature**.
- Save a dish or a whole meal as a named recipe:
  - lines (shared / own amount), split mode, remembered own amounts per person
  - shared by the household
  - **no scaling** (the user declined ×½/×2): it fills Cook as saved.
- Recipe lines reference the ingredient, so cooking it uses the current ingredient values. Custom
  items keep their own values.
- Tables `recipes` + `recipe_lines` (+ own amounts), household RLS.
- Entry points:
  - "Save as recipe" in the dish editor and on a logged meal
  - a **Recipes** list on Cook: tap one to fill the Cook draft (`cookDraft.ts`), with rename,
    edit and delete.
- **Copy a meal** to another day and meal (and person) from the meal sheet. It creates a new dish
  through `save_dish`, so totals and live updates work as usual.

- **User decisions (2026-10-20):** a whole meal saved as a recipe is **merged into one dish**
  (Cook holds one dish at a time); a copied meal **keeps the original values** (logged snapshots
  and amounts), also when copied to the partner.
- **As built (2026-10-20):**
  - DB (`20261020100000_recipes`): `recipes`, `recipe_portions` (user or null = leftover, split
    value), `recipe_lines` (ingredient link + snapshot), `recipe_line_amounts`; household read
    RLS, writes only via `save_recipe` (create or replace, last save wins, same checks as
    `save_dish`) and `delete_recipe`; a broadcast trigger on `recipes` sends `{table:'recipes'}`
    through the generic `live_change_of` branch.
  - App: `recipes/recipeModel.ts` (`recipeFromDish`: each person once, later portions and thrown
    away ones become leftovers; `recipeFromMeal`: what that person ate, shared lines, one portion;
    `dishFromRecipe`: new ids, current ingredient values unless the ingredient is gone or lost the
    unit). `CookDraft.recipeId` remembers the recipe Cook was filled from, so **Save as recipe**
    offers "Update …" or "Save as new recipe" (that's how a recipe's ingredients are edited).
