# Build plan, 2026-10-15

The working plan for README items 1–15 ("Fixes and improvements (planned)"). The README has the
user-facing wording; this file has the decisions, the technical approach and where to start, so a
new session can pick up any item. **Update the status table after every item** (commit ref), and
tick the item in the README in the same commit.

## How to work on this project

- **Plan approved 2026-10-15? → see Status.** Once the user has approved, build every item back to
  back without stopping between them. Stop only for a real question, or where an item says
  "user picks".
- **TDD**: write the failing test first (Vitest + Testing Library next to the file, `*.test.ts(x)`;
  DB behavior in `supabase/tests/*.test.ts` against the DEV project; user journeys in
  `e2e/journeys/*.spec.ts`). Coverage must stay ≥ 80 % (`pnpm coverage` enforces it).
- **Before every push**: `pnpm lint && pnpm typecheck && pnpm format:check && pnpm test`, the
  affected e2e journeys (see README › Development; in WSL add `E2E_BROWSER=chromium`), and
  `pnpm test:db` when migrations changed.
- **Push to `main`** (Vercel deploys it). Don't wait for CI: report at once, and check the
  previous run (`gh run list`) at the start of the next item. If it's red, fix that first.
- **Commits**: conventional (`feat:`, `fix:`, …), one per item or step. **The README is updated in
  the same commit** as any feature, setup, CI or architecture change.
- **Migrations**: `supabase/migrations/<yyyymmddhhmmss>_<name>.sql`. Push to **DEV first**
  (CLI is normally linked to dev), run `pnpm test:db`, then link PROD, push, and relink DEV.
  Regenerate `src/lib/database.types.ts` with `pnpm db:types`. Prod pushes may be blocked by
  the permission classifier. If so, commit locally, don't push app code that needs the
  migration, and ask the user.
- **UI copy**: short, neutral, professional ("Save", "Log meal"). No playful or personal text.
  Partner nicknames only where a person is identified (`useLookOf()`).
- **Settings are account-bound**: preferences live on the profile (`profiles.appearance` jsonb
  or a new column), never device-only. localStorage only as a launch cache.
- **iPhone**: a 390×844 home-screen PWA on iOS 27. No browser emulates its safe areas or
  viewport quirk. Never remove `--viewport-shortfall` or `stable-paint-layer` as dead code.
  The user can't send screenshots. Ask them for on-device confirmation in words.
- **Scripted edits**: read a file into a variable before `open(p, 'w')`, and check for empty
  files afterwards.
- Never: water tracking, invite-code rotation, xtool (checked 2026-10-15: device-only native
  builds, no iOS Simulator on Linux, doesn't help testing a PWA).

### 3 · Ingredient edits reach meals of the last 14 days

- Decision: **automatic**, window = **today and the 13 days before** (rolling, by the meal's
  local date), **both people's meals**. Older meals keep their snapshot. After saving, a toast:
  "Updated in N meals" (nothing when N = 0).
- This reverses part of the snapshot design (README › Features says "editing an ingredient
  later never changes past meals"). Update that README sentence when it ships.
- **As built (2026-10-15):** done in the app, not as an RPC, to reuse the tested `buildMealItem` /
  `resolveAmount` instead of porting them to SQL: `ingredients/applyToRecentMeals.ts` (plain items
  updated directly, dishes saved as a new revision through `save_dish`), triggered by
  `IngredientSheet`'s `onUpdated` on the Ingredients tab. Journey: `e2e/journeys/recent-meals.spec.ts`.
- Original idea: an RPC `apply_ingredient_to_recent_meals(p_ingredient_id, p_since date)` (security
  invoker or a checked definer, household-scoped):
  - update the `meal_items` snapshot of plain items with that ingredient in meals ≥ `p_since`
  - update the `dish_lines` snapshot of dishes that have a portion in the window, bump the dish
    revision, and re-log them with `private.log_dish_portions(dish_id)`
  - return the number of distinct meals touched.
- The client passes `p_since` = local today − 13 (`lib/dates`). Call it right after a
  successful ingredient update, then invalidate the day/history queries. Live hints already
  fire from the table triggers.
- Tests: `supabase/tests/` (plain item and dish inside/outside the window, the other member's
  meal, another household untouched), plus the unit test for the toast.

### 2 · Keep-alive for prod and dev

- Both Supabase projects (prod `cal-calculator-2`, dev `cal-calculator-dev`; refs in
  `.env.local` / `.env.test.local`).
- **As built (2026-10-15):** the anon role can't read any table (`permission denied`), so the
  workflow calls a new harmless RPC `public.keep_alive()` (migration `20261015120000_keep_alive.sql`,
  on dev and prod) with each project's anon key. Repo secrets `SUPABASE_PROD_URL` and
  `SUPABASE_PROD_ANON_KEY` were added.
- Approach: a scheduled GitHub Actions workflow `.github/workflows/keep-alive.yml` (e.g. every
  2 days, plus `workflow_dispatch`) doing one real PostgREST read on each project.
  - It needs repo secrets for the prod URL + anon key. The dev ones (`SUPABASE_TEST_*`) exist.
  - Anon + RLS returns nothing, but the request still reaches the database.
- Caveat for the README: GitHub turns off scheduled workflows after 60 days without repo
  activity. If that's a concern, a Vercel cron is the fallback.
- Document it in README › Deployment.

### 9 · Read nutrition labels (on-device)

- Decision: **on-device OCR** (no AI service). It must work offline after first use and must
  only load when first used.
- Approach: `tesseract.js`, lazy `import()`, German + English trained data. Serve or cache the
  language files so they work offline (Workbox runtime cache).
- Pure, well-tested parser `labelParser.ts`:
  - finds the per-100 g/ml column
  - maps row names (DE: Brennwert/Energie, Fett, davon gesättigte Fettsäuren, Kohlenhydrate,
    davon Zucker, Ballaststoffe, Eiweiß, Salz; EN equivalents)
  - handles kJ/kcal and decimal commas.
- Entry point: a **Read label** button next to the barcode scan in the ingredient form (camera
  or photo).
- It fills the form like the Open Food Facts prefill (`barcode/useProductPrefill.ts`,
  `PrefillNote`), the user checks, and **it never saves by itself**. `valueChecks` warnings
  still apply.

### 10 · Push notifications

- Also finishes item 1: the weekly odd-values push. The in-app part is `needsCheck()` in
  `ingredients/valueChecks.ts` (rules from `valueWarnings`), shown by `IngredientRow` and the
  `ListOptions` check chip.

**Decisions:**

- Events: **partner changes your day** (they log, edit or delete a meal for you, or share a
  dish with you), **unsaved Cook dish**, **meal reminders**, **day summary**, **odd ingredient
  values** (item 1).
- **Everything is per person and saved to the account**: each kind on/off, and every time is
  editable.
- Defaults:
  - summary the **next morning at 08:00 about the day before** (evening snacks count). Per
    person, it can be the same day at any time (e.g. 23:00)
  - reminders breakfast 10:00, lunch 14:00, dinner 20:00, each on/off: a reminder fires only if
    that meal is still empty
  - unsaved Cook dish after **30 min** without a change
  - partner changes are **grouped** (send once a few minutes pass with no new change)
- A **Send test notification** button.
- The user declined weekday schedules and quiet hours.

**Approach** (the largest item; check the API details against current docs):

- Service worker: switch `vite-plugin-pwa` from generateSW to **injectManifest** with
  `src/sw.ts`. It keeps the precache and the prompt-update flow (`registerServiceWorker.ts`,
  `updateReady.ts`) and adds `push` and `notificationclick` handlers (open the relevant tab/day).
  Re-run the offline and version journeys.
- Client:
  - Settings › Notifications is a sub-page via `usePagePath`, like Appearance
  - permission is requested on a tap, and only in standalone mode (iOS rule)
  - `pushManager.subscribe` uses the VAPID public key (`VITE_VAPID_PUBLIC_KEY`)
  - the subscription is stored per device.
- DB (migration):
  - `push_subscriptions` (user, endpoint unique, keys, last success)
  - `profiles.notification_settings` jsonb (Zod-parsed with defaults on the client) and
    `profiles.time_zone`, set from the device
  - a sent-log for dedupe (kind + key, e.g. summary per date, reminder per date + meal)
  - a queue of partner-change notices, written by a trigger when `auth.uid()` ≠ the meal owner.
    Reuse what `private.live_change_of` knows.
- Server:
  - Supabase Edge Function(s) in Deno sending Web Push (`npm:web-push`). VAPID keys are function
    secrets.
  - a `pg_cron` job every ~5 min calls the tick function via `pg_net` with a shared secret. It
    handles reminders, summaries, unsaved drafts, grouped partner notices and odd values (weekly).
  - a test endpoint, authorized by the user's JWT, for the test button
  - expired subscriptions (404/410) get deleted.
- Both projects (dev and prod) need the functions deployed, secrets set and the cron scheduled.
  Document all of it in README › Deployment / Development.
- Testing:
  - unit-test the pure scheduling logic: given settings + time zone + now + day data, what is
    due
  - DB tests for the triggers and queue
  - an e2e journey with a mocked push for the settings page.
- Real delivery needs the user's iPhone.

### 11 · Unsaved Cook dish

- "Unsaved" = a Cook draft with content that was never logged.
- **Badge on the Cook tab** (`TabShell.tsx`). This part can ship before item 10.
- For the push, the server must see the draft:
  - a `cook_drafts` table (user pk, draft jsonb, `updated_at`), upserted debounced from
    `features/cook/draftStorage.ts` / `useCookDraft.ts`
  - the local copy stays the source of truth offline
  - the row is deleted on Log / clear.
- The tick from item 10 sends one push per draft version, after the user's delay.

### 12 · Quick picks

- **Favorites per person**: table `ingredient_favorites(user_id, ingredient_id)`, RLS own rows.
  A star on the ingredient row/sheet.
- **Recent**: your own last-used distinct ingredients. Use an RPC like `ingredient_use_counts`,
  or derive it from your meal items.
- Shown at the top of the Cook ingredient search before typing, and as filter chips in both
  ingredient lists (next to the brand filter).

### 13 · Cheat days and eating out

- **Cheat day**: a per-person day flag, e.g. table `day_flags(user_id, date, cheat_day)`.
- **Eaten out**: a flag on the meal (`meals.eaten_out`; empty meals too, via `ensure_meal`).
  Food in it is optional. A day with an eaten-out meal is "unknown": it shows
  "≥ N kcal · eaten out" instead of an exact total.
- Both:
  - a badge in History (calendar) and on Today
  - **left out of Trends averages** (`features/trends/trends.ts`)
  - **no over-goal look** on the rings that day.
- Settable, changeable and removable on **any day, past ones too**, by either household member
  (same RLS as meals).
- Extend `daily_totals` (or the client day model) with both flags, and add live hints for the
  new table/column.
- Copy stays neutral ("Cheat day", "Eaten out").

### 14 · Recipes (+ copy a meal)

- Decision: recipes and meal templates are **one feature**.
- Save a dish or a whole meal as a named recipe:
  - lines (shared / own amount), split mode, remembered own amounts per person
  - shared by the household
  - **no scaling** (the user declined ×½/×2): it fills Cook as saved.
- Recipe lines reference the ingredient, so cooking it uses the current ingredient values. Custom
  items keep their own values.
- Tables `recipes` + `recipe_lines` (+ own amounts), household RLS.
- Entry points:
  - "Save as recipe" in the dish editor and on a logged meal
  - a **Recipes** list on Cook: tap one to fill the Cook draft (`cookDraft.ts`), with rename,
    edit and delete.
- **Copy a meal** to another day and meal (and person) from the meal sheet. It creates a new dish
  through `save_dish`, so totals and live updates work as usual.

### 15 · Export

- Settings › Export: pick a date range. The data is **both members'** (person column).
- Files:
  - foods: person, date, meal, food, brand, amount, unit, kcal + nutrients in label order,
    estimate
  - days: person, date, totals, weight, cheat day, eaten out.
- On iOS, hand both CSV files over with `navigator.share({ files })`, with a download fallback.
- Unit-test the CSV builder (escaping, decimal format, empty days).
